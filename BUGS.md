## [BUG] Cloud deploy: server created but IP never assigned (no SSH access)

**Severity:** Critical  
**Date:** 2026-08-14  
**Affected:** All new cloud deploys (htz-0, htz-13, multiple regions)

### Symptom
Stacker creates a Hetzner server via Terraform but the deployment finishes with status `paused` and `server_ip: null`. The SSH key is saved locally but never installed on the server. 75+ servers have no IP assigned.

### Root Cause (from Terraform logs)
```
Error: unsupported location for server type (invalid_input): []
```
The `cpx21` server type is not available in `nbg1` (Nuremberg). Terraform fails but the error is swallowed — Stacker marks deployment as "paused" instead of "failed".

Even after fixing the region to `fsn1`, the same issue occurred — suggesting the IP parsing from Terraform output may also be broken.

### Steps to Reproduce
1. `cd stacker-projects/nocodb`
2. `stacker deploy --target cloud --key htz-0 --force-new --watch`
3. Deployment finishes with `paused` status, no IP

### Expected
Server created with IP assigned, SSH key installed, deployment completes.

### Actual
Server created in Hetzner, IP never returned to Stacker API, SSH key orphaned locally.

### Fix Needed
1. ~~Validate server type availability per region before Terraform apply~~ — Use `cpx22` instead of `cpx21`
2. Properly surface Terraform errors (not just "paused")
3. Fix IP parsing from Terraform output when server creation succeeds

### Resolution (2026-08-15)
`cpx22` in `fsn1` works. `cpx21` is not available in `nbg1` or `fsn1`.

## [BUG] StackPilot cloud deploy fails — `.stacker` directory not created on server

**Project:** stackpilot  
**Server:** 46.224.139.90 (Hetzner fsn1, cpx32)  
**Error:**
```
resolve : lstat /home/trydirect/.stacker: no such file or directory
```

**Root cause:** Ansible playbook tries to access `/home/trydirect/.stacker` on the remote server, but the directory wasn't created during the deployment process. The deployment completed Docker installation and image pulls but failed at the compose deployment step.

**Impact:** Deployment paused, server created but unreachable (no SSH key installed).

**Fix needed:** Stacker should create the `.stacker` directory on the remote server before attempting to deploy compose files.

## [BUG] Supabase cloud deploy — DB role passwords missing

**Project:** supabase  
**Server:** 88.198.151.116 (Hetzner fsn1)  
**Error:**
```
FATAL: password authentication failed for user "authenticator"
User "authenticator" has no password assigned.
```

**Root cause:** The `supabase/postgres` image requires additional environment variables for role passwords (`AUTHENTICATOR_PASSWORD`, `SUPABASE_AUTH_ADMIN_PASSWORD`, etc.) that are not set in the stacker.yml. Multiple services (auth, rest, realtime, storage, functions) fail to connect.

**Fix needed:** Add missing role password env vars to the db service in stacker.yml.

## [BUG] Cloud deploy: Hetzner resource limit error not surfaced in deploy output

**Severity:** Medium  
**Date:** 2026-08-17  
**Affected:** All cloud deploys when Hetzner account hits resource limits

### Symptom
`stacker deploy --target cloud --force-new --watch` shows:
```
Deployment still in progress (Creating server infrastructure), waiting for IP...
...
Deployment #675 finished with status 'paused' — server IP may not be available.
Server found but IP not yet assigned (attempt 1/6), retrying in 10s...
```

The actual error is only visible in `stacker deployment events`:
```
Error: network limit reached (resource_limit_exceeded, 1b09dc9ad070d4d2689182f997167b67)
```

### Root Cause
Hetzner API returns `resource_limit_exceeded` but Stacker's `--watch` mode doesn't surface this error. It only shows "server IP not yet assigned" and retries, then marks as "paused".

### Expected
The deploy command should show the actual Hetzner error immediately:
```
Error: Hetzner resource limit reached. Delete unused servers or increase limits.
```

### Actual
User sees generic "IP not assigned" messages and has to run `stacker deployment events` to find the real error.

### Fix Needed
1. Surface Hetzner API errors in the `--watch` output
2. Don't retry when the error is `resource_limit_exceeded` — it won't resolve on its own
3. Show actionable message (e.g., "Delete unused servers or increase Hetzner limits")
