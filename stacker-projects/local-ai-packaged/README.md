# local-ai-packaged

[coleam00/local-ai-packaged](https://github.com/coleam00/local-ai-packaged) as one
stacker project: n8n, Supabase, Ollama, Open WebUI, Flowise, Qdrant, Neo4j,
SearXNG, Langfuse and Caddy (28 services).

## Deploy

One click, from the baked image (all images and the Ollama models already on
the server, fresh secrets per install):

https://try.direct/quick-deploy?source=github&repo=trydirect/awesome-selfhosted-stacker&path=stacker-projects/local-ai-packaged&ref=fe92a7327b3b08d0d2a56c23459346967b986b35

Or with the stacker CLI:

```bash
./scripts/generate-secrets.sh            # .env with fresh secrets
stacker deploy --target local            # this machine
stacker deploy --target cloud --force-new   # Hetzner cpx42 (8 vCPU, 16 GB)
```

Caddy serves every UI on its own port:

| Port | UI |
|---|---|
| 8001 | n8n |
| 8002 | Open WebUI |
| 8003 | Flowise |
| 8005 | Supabase Studio (login `DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD` from `.env`) |
| 8007 | Langfuse |
| 8008 | Neo4j Browser - open `/browser/` |

Plan for 16 GB of RAM: the 7B model alone takes 5-6 GB while loaded.

## Ollama: CPU or GPU

By default Ollama runs on the CPU and pulls `qwen2.5:7b-instruct-q4_K_M` and
`nomic-embed-text`. On your own hardware set in `.env`:

| Machine | `.env` |
|---|---|
| CPU only (default) | `OLLAMA_CPU_REPLICAS=1` |
| NVIDIA GPU | `OLLAMA_CPU_REPLICAS=0`, `COMPOSE_PROFILES=gpu-nvidia` |
| AMD GPU (ROCm) | `OLLAMA_CPU_REPLICAS=0`, `COMPOSE_PROFILES=gpu-amd` |
| No local models | `OLLAMA_CPU_REPLICAS=0` |

Every variant answers as `ollama` on the network, so the other services need
no change.

## How the services are built

`services:`, `volumes:` and `config_contract` in `stacker.yml` are generated by
`scripts/build-services.py` from the upstream sources at pinned commits:
local-ai-packaged itself, Supabase's self-hosting compose and Langfuse's
compose (upstream still uses `minio/minio`, which is no longer published).
Edit the script, not the generated block, then run:

```bash
uv run --with pyyaml python3 scripts/build-services.py
```

CI runs it with `--check` and fails when the committed block differs.

What the script changes from upstream, and why, is listed in its docstring:
pinned images, directory mounts turned into named volumes or single-file
mounts, only Caddy publishing ports, secrets read through `environment` so a
baked image never keeps them literal.

## Secrets and Quick Deploy

Each secret has one key in `.env` (`JWT_SECRET`, `POSTGRES_PASSWORD`, ...); the
services read it under their own names as `${KEY}` references. `config_contract`
declares how each key is regenerated per install - Supabase's `ANON_KEY` and
`SERVICE_ROLE_KEY` are JWTs re-signed with the new `JWT_SECRET`. Only the
Ollama model volume survives into a baked image; every other volume starts
empty, so no database keeps the author's credentials.

## Known limits

- Neo4j Browser loads from `:8008/browser/`, but connecting it to the
  database needs Bolt on port 7687, which Caddy does not publish (as upstream).

- Supabase, Langfuse and n8n are configured for `http://localhost` URLs
  (`SITE_URL`, `API_EXTERNAL_URL`, `SUPABASE_PUBLIC_URL`). Set them to your
  domain before using Supabase Auth email links or Langfuse login redirects.
- `depends_on` conditions, `container_name`, clickhouse's `user` and log
  rotation from upstream have no stacker.yml field and are left out; services
  restart until their dependencies are ready.
